### D8-01 · Critique · Hors ligne, une modification « enregistrée au retour de la connexion » est perdue si l'on ferme CIPL avant ce retour, sans aucun avertissement
- Où : `Assets/Script/Cloud/EcritureCloud.cs:203-219` (`_enAttente` : un `HashSet` statique, en mémoire seulement ; `MettreEnAttente` : « Hors ligne : « X » sera enregistré au retour de la connexion »), `:270` et `:309` (les deux entrées : saisie commencée avant la coupure, écriture coupée en route), `:94-101` (`GarderCopie` écrit `_cache`, l'état connu du serveur, pas `_enAttente`), `Assets/Script/Cloud/CopieLocale.cs:84-89` ; `Assets/Script/General/FermetureGuard.cs:103-113` (la garde ne regarde que les fiches en saisie, les écrans tenus et `EnregistrementEnCours`, faux hors ligne puisque rien n'entre dans `_file`) ; `EcritureCloud.cs:664-668` (un écran fermé quitte `_tenus` au passage suivant du gardien).

### D8-02 · Majeur · Une confirmation qui s'ouvre pendant un message d'erreur l'efface : la suite du message ne s'exécute jamais (correction D2-05 incomplète)
- Où : `Assets/Script/Tools/ConfirmDialog.cs:39-44` (`Erreur` attend son tour seulement derrière une fenêtre déjà ouverte), `:64-85` (`Show` remplace sans condition `_onConfirm`, donc l'`ensuite` d'une erreur affichée) ; appelant typique : `Assets/Script/General/FermetureGuard.cs:123-127` (croix de la fenêtre Windows ou Alt+F4 → `Show` ; ce clic ne passe pas par l'interface Unity, la fenêtre plein écran du dialogue ne le bloque donc pas) ; `Assets/Script/Cloud/EcritureCloud.cs:486-503` (`Abandonner` : `Erreur(message, () => { _abandonEnCours = false; FermerEcrans(); DemarrageCloud.Recharger(); })`, et `if (_abandonEnCours) return;`).
- Problème : D2-05 a mis les erreurs en file entre elles, mais une confirmation (`Show`) qui arrive pendant une erreur la remplace au lieu d'attendre : l'`ensuite` de l'erreur est perdu. Ce sont justement les `ensuite` que D2-05 voulait sauver (relecture d'une fiche, perte de verrou).
- Scénario : un admin libère de force « Volteo » pendant que Marie la modifie : message au centre « … vos saisies non enregistrées sont annulées » (OK = fermer les écrans et relire). Ses saisies restent derrière pour être recopiées ; Marie clique la croix de la fenêtre : « Modifications non enregistrées … Vous pouvez annuler » remplace le message ; elle clique « Annuler » pour recopier d'abord. La suite est perdue : `_abandonEnCours` reste vrai jusqu'au redémarrage, les écrans ne se ferment pas, l'entreprise n'est pas relue ; la prochaine perte de verrou de la session est ignorée en silence (`Abandonner` sort tout de suite) et Marie saisit sur une fiche qu'une autre personne tient : son « Enregistrer » sera refusé.
- Correction proposée : dans `MontrerErreur`, garder l'erreur affichée (`_erreurCourante = (message, ensuite)`, remise à null quand on clique « OK ») ; dans `Show`, si `_erreurCourante != null`, la remettre de côté avant d'afficher la confirmation ; `Suivant()` la remontre en premier, avant la file. Variante plus courte : mettre la confirmation elle-même en attente quand une erreur est affichée.
- Test : EditMode, ConfirmDialog monté sur un GameObject avec ses deux boutons et deux textes : `Erreur("A", ensuite)`, puis `Show(...)`, clic « Annuler » → la fenêtre remontre « A » ; clic « OK » → `ensuite` exécuté une fois.
- Confiance : haute sur le code ; moyenne sur la fréquence (il faut une confirmation pendant un message d'erreur ; la croix Windows en est le cas le plus simple).

### D8-04 · Majeur · `SaisieNumerique` lit « 2.500.000 » comme 2 500 : un séparateur répété est pris pour la virgule
- Où : `Assets/Script/Tools/SaisieNumerique.cs:36-45` (le dernier « . » ou « , » devient décimal, même quand ce signe apparaît plusieurs fois) ; utilisé par `ParseOuAvertir`, `ParseOuAvertirD` et `Parse` (achats, travaux, calcul rapide, et les panneaux qui avaient leur propre `ParseF`) ; `Assets/Editor/Tests/SaisieNumeriqueTests.cs:52-58` (seul « 1.234.567,89 » est testé).
- Problème : la règle « seul le dernier séparateur est décimal » est juste quand il y a deux sortes de séparateurs. Avec une seule sorte, répétée, aucun ne peut être décimal (un nombre n'a qu'une virgule), mais le code prend quand même le dernier. La saisie est acceptée sans avertissement (`TryParse` renvoie vrai).
- Scénario : prix d'achat d'un immeuble tapé « 2.500.000 » (écriture qu'on voit souvent) → 2 500,000, soit 2 500 € ; « Investi » de l'accueil faux d'un facteur 1 000 et « Rendement net » multiplié d'autant. Même chose pour « 1,250,000 » → 1 250. Les clients visés (sociétés foncières) saisissent des prix en millions. « 1.200 » seul reste 1,2 : c'est la décision documentée, inchangée.
- Correction proposée : juste avant la normalisation : `char sep = net[indexDecimal]; char autre = sep == '.' ? ',' : '.'; if (net.Count(ch => ch == sep) > 1 && net.IndexOf(autre) < 0) net = net.Replace(sep.ToString(), "");` (tous des milliers), sinon le code actuel.
- Test : EditMode, `SaisieNumeriqueTests` : `Un_separateur_repete_est_un_groupement_de_milliers` (« 2.500.000 » → 2 500 000 ; « 1,250,000 » → 1 250 000 ; « 1.234.567,89 » inchangé ; « 1.200 » → 1,2 inchangé).
- Confiance : haute sur le calcul ; moyenne sur la fréquence (dépend des habitudes de saisie ; les espaces, eux, marchent).
