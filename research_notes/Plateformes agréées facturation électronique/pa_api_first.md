## 2. API publique : documentation, dépôt d'un Factur-X déjà produit, statuts de cycle de vie, réception, authentification, sandbox, SDK

### Takeaway
**B2Brouter** est le seul candidat dont la doc publique décrit noir sur blanc un endpoint d'import d'un Factur-X PDF déjà produit (`POST /accounts/{id}/invoices/import`), ainsi que le mapping de ses statuts sur les codes CDV, les webhooks, le staging et les comptes par SIREN. **Super PDP** a une API REST OAuth2 simple : on dépose un fichier, on suit des événements (`fr:212`…), on relève les factures reçues par polling, et un endpoint convertit JSON + PDF en Factur-X. Elle est encore en `v1.beta` et sa doc n'est pas lisible sans navigateur. **Iopole** annonce doc libre, Swagger, sandbox et webhooks, mais je n'ai pas pu lire son portail. **Invopop** est centrée sur le JSON GOBL : le dépôt d'un Factur-X existant n'est pas documenté.

### Cited Findings
**Super PDP**
- Base `https://api.superpdp.tech`. Authentification OAuth2 : `POST /oauth2/token` en `client_credentials` (un couple client_id/secret par entreprise, vendeur ou acheteur), puis `Authorization: Bearer`. Endpoints de l'exemple : `GET /v1.beta/companies/me`, `GET /v1.beta/invoices/generate_test_invoice?format=ubl`, `POST /v1.beta/validation_reports` (multipart `file`), **`POST /v1.beta/invoices` (corps = le fichier facture, UBL dans l'exemple)**, `GET /v1.beta/invoices?starting_after_id=…` (**polling des factures reçues**), `GET /v1.beta/invoices/{id}`, **`POST /v1.beta/invoice_events` avec `status_code: "fr:212"` (« Encaissée »)** et les montants encaissés par taux de TVA — [GitHub superpdp/examples, quick_start.js](https://raw.githubusercontent.com/superpdp/examples/main/quick_start.js) (dépôt mis à jour le 31/08/2026).
- Conversion : `POST /v1.beta/invoices/convert?from=cii&to=en16931`, puis `POST /v1.beta/invoices/convert?from=en16931&to=factur-x` (multipart : `invoice` en JSON et `pdf` en PDF) → un fichier Factur-X validable par `/validation_reports` — [facturx.js](https://raw.githubusercontent.com/superpdp/examples/main/facturx.js).
- Exemple ERP en OAuth2 *Authorization Code* (`/oauth2/authorize`) : le logiciel redirige l'utilisateur vers le « tunnel d'inscription SUPER PDP », puis récupère un token pour cette entreprise — [erp.go](https://raw.githubusercontent.com/superpdp/examples/main/erp.go).
- API REST avec webhooks et JSON, documentation OpenAPI gratuite, moins de 300 ms de réponse, jusqu'à 30 appels/s par clé, sandbox ; formats Factur-X, UBL, CII et JSON — [digitiz.fr (16/10/2026)](https://digitiz.fr/superpdp/). Webhooks pour les statuts et bac à sable également cités par [comparepdp.com](https://comparepdp.com/articles/api-facturation-electronique) (non daté, « © 2026 »).
- Documentation officielle à `superpdp.tech/documentation` (« Guides de développement et référence API ») et page de statut `status.superpdp.tech`. Certifiée ISO 27001 (LNE) et Peppol AP et SMP — [superpdp.tech](https://www.superpdp.tech/). La page de doc est rendue en JavaScript : WebFetch n'a récupéré que le titre.

**B2Brouter**
- Authentification par clé API : en-tête `X-B2B-API-KEY` ou Basic auth avec la clé comme identifiant. API versionnée par date (dernière version v2026-06-26). **Environnement de staging séparé** (`app-staging.b2brouter.net`, avec des clés distinctes de la production). Pages SDKs, Sandbox et Webhooks — [docs.b2brouter.net, vue d'ensemble](https://docs.b2brouter.net/en/get-started/overview/) ; [developer.b2brouter.net](https://developer.b2brouter.net), via un extrait de recherche.
- **Import d'un fichier existant : `POST /accounts/{id}/invoices/import`, qui accepte `application/pdf` (Factur-X PDF/A-3) et `application/xml` (UBL 2.1 / CII).** On peut aussi envoyer du JSON (`POST /accounts/{ACCOUNT_ID}/invoices`) et B2Brouter génère alors l'UBL, le CII ou le Factur-X — [guide France DGFiP](https://docs.b2brouter.net/en/developers/guides-by-country/france/dgfip-e-invoicing-and-e-reporting/).
- Statuts de cycle de vie des factures émises : `sending`, `sent` (CDV 200 Déposée), `registered` (202 Reçue), `read` (204), `accepted` (205/206), `annotated` (207), `refused` (210), `paid` (212), `error`. Suivi par webhooks (Settings → Webhooks) ou par polling de `GET /invoices/{id}` ; `POST /invoices/{id}/mark_as` pour poser un statut. Annuaire : `GET /directory/fr/0009/{siret}` (flux 11). E-reporting : flux 1, 6 et 10 — [même guide](https://docs.b2brouter.net/en/developers/guides-by-country/france/dgfip-e-invoicing-and-e-reporting/).
- Autres canaux sans code : SFTP, « B2Bconnector for Windows », eSender/eReceiver, ainsi qu'un connecteur MCP — [docs.b2brouter.net](https://docs.b2brouter.net/en/get-started/overview/).

**Iopole**
- Page « Développeurs » : accès libre à la documentation technique et sandbox qui simule les statuts (acceptée, refusée, en litige, paiement envoyé…) — [iopole.com/developpeurs](https://www.iopole.com/developpeurs), via un extrait de recherche ; la page a échoué au fetch (erreur d'en-tête HTTP). Statuts récupérables en webhook ou en pull — [iopole.com/e-reporting](https://www.iopole.com/e-reporting), via un extrait de recherche.
- Formats Factur-X, UBL et CII, « API REST & Swagger », point d'accès Peppol, ISO 27001 et SecNumCloud — [facture-electronique-en-ligne.fr (26/05/2026)](https://facture-electronique-en-ligne.fr/avis-logiciel/iopole). Sandbox, doc API, Swagger, page d'uptime, « POC en quelques heures », plus de 150 millions de documents par an — [codeur.com](https://www.codeur.com/blog/plateforme-agreee-editeur-de-logiciels/) (**article sponsorisé par Iopole**, ~mars 2026).
- `docs.iopole.com` existe mais est rendu en JavaScript : WebFetch n'a récupéré que le titre « Iopole ».

**Invopop**
- Une facture GOBL (JSON) peut générer et envoyer tous les formats français (UBL, CII, Factur-X). L'enregistrement de chaque partie (SIREN) dans l'Annuaire et sur Peppol est un prérequis unique. Statuts en CDAR, flux 6 (déposée, rejetée, refusée, encaissée) ; codes 210 et 212 transmis au PPF — [docs.invopop.com/guides/fr-pa](https://docs.invopop.com/guides/fr-pa.md). Les 14 statuts reviennent à l'émetteur ; enregistrement, facturation et cycle de vie disponibles, e-reporting (flux 10) en développement — [invopop.com/coverage/france](https://invopop.com/coverage/france), via un extrait de recherche.

**Seqino** : « API RESTful », SDK dans plusieurs langages (non nommés), étape « Test de la sandbox » — [seqino.com](https://seqino.com/api-pdp-marque-blanche-grise-facture-electronique/). Webhooks, dépôt de Factur-X et statuts ne sont pas mentionnés.
**Docoon** : API REST, portail web, automate Windows, environnement de test, point d'accès Peppol — [comparatif-facture-electronique.fr](https://www.comparatif-facture-electronique.fr/docoon-facturation-electronique-avis/), via un extrait de recherche.
**Jefacture** : vise surtout les experts-comptables et leurs clients TPE/PME (suite ECMA, plus de 4 000 cabinets) ; aucune API éditeur confirmée — [comparatif-facture-electronique.fr](https://www.comparatif-facture-electronique.fr/jefacture-com-ecma-facturation-electronique-avis/), via un extrait de recherche.

### Inferences
- Pour CIPL, qui produit déjà ses Factur-X : B2Brouter est le seul candidat dont le chemin « je dépose mon PDF Factur-X » est documenté publiquement. Chez Super PDP, `POST /v1.beta/invoices` prend le fichier brut et Factur-X est un format accepté : le dépôt direct d'un Factur-X est très probable, mais l'exemple public n'envoie que de l'UBL. À confirmer dans `superpdp.tech/documentation`.
- Avec Invopop, CIPL devrait probablement envoyer du GOBL JSON plutôt que son propre Factur-X : c'est une refonte de son pipeline.
- Super PDP expose l'API d'événements (`invoice_events`) qui permet de déclarer « Encaissée » (212), utile pour un logiciel de gestion locative qui connaît les encaissements de loyers.
- L'API Super PDP est en `v1.beta` : il faut prévoir des changements de contrat d'API.

### Gaps
- Doc de référence Super PDP (liste des webhooks, schéma de `POST /invoices` pour un PDF Factur-X) et doc Iopole : portails rendus en JavaScript, non lus. Une session navigateur serait nécessaire.
- Réception chez B2Brouter : le détail de l'endpoint de récupération des factures reçues n'a pas été lu (page « Receive, integrate and manage received invoices » de docs.b2brouter.net non consultée).
- SDK Super PDP : seuls des exemples JS et Go sur GitHub, pas de SDK officiel trouvé.

## 3. Tarifs : à la facture, abonnement, mise en place, gratuit, modèle éditeur, et coût pour une petite SCI

### Takeaway
Seuls **Super PDP**, **B2Brouter** (offres « entreprise ») et **Invopop** publient des prix. Super PDP est de loin le moins cher pour l'intégration API : 0,01 € HT par facture jusqu'à 10 000 par mois, 2 € HT par vérification KYC/KYB et 10 € HT de minimum par an. B2Brouter coûte 110 € HT par an et par société en offre Professional, mais son offre éditeur (eDocSync) est sur devis. Iopole, Seqino, Docoon et Jefacture sont sur devis ou non publics. Invopop facture 0 € (Dev, 200 « Pops ») ou 500 € par mois (Pro).

### Cited Findings
- **Super PDP, page tarifs (non datée)** : offre Compte gratuite de 0 à 1 000 factures par mois (au-delà, « Le compte bascule sur l'offre API et sa tarification à la facture ») ; offre API par palier mensuel : **0,01 € HT par facture de 0 à 10 000, 0,005 € de 10 000 à 100 000, 0,0025 € au-delà de 100 000** ; « Minimum de facturation (au global) : 10,00 €HT par an » ; « Vérification KYC / KYB : 2,00 €HT » ; aucun frais de mise en place mentionné ; une journée d'e-reporting de caisse compte comme une facture ; **marque grise : l'éditeur paie Super PDP au tarif de gros et peut refacturer ses clients ; la marque SUPER PDP apparaît à l'inscription du client** ; marque blanche non confirmée (« contacter ») — [superpdp.tech/tarifs](https://www.superpdp.tech/tarifs). Mêmes chiffres chez [digitiz.fr (16/10/2026)](https://digitiz.fr/superpdp/), qui ajoute que la réception est incluse dans le compte gratuit.

### Inferences
- **Super PDP, simulation** (calcul à partir des prix publics, sans confirmation du fournisseur) : une SCI à 30 factures par mois fait 360 factures par an, soit **3,60 € HT par an**, plus 2 € HT de KYC une fois. Pour 5 SCI à 30 factures par mois : 1 800 factures, soit 18 € HT par an, plus 10 € de KYC ; le minimum de 10 € par an « au global » est donc dépassé. Si les factures reçues sont aussi facturées à 0,01 €, le coût reste de l'ordre de quelques euros par an et par SCI. À cette échelle, c'est négligeable face à un abonnement Pennylane par société.
- **B2Brouter** : si chaque SCI prend un plan Professional, 110 € HT par an et par SCI, réception comprise. Une SCI exonérée de TVA pourrait tenir sur Basic gratuit (24 transactions par an), mais une SCI qui émet chaque mois plusieurs quittances dépasserait vite ce plafond. Le coût réel côté éditeur (eDocSync) est inconnu.
- **Invopop** : avec 100 à 200 Pops par mois et par SCI, le plan Dev (200 Pops) ne couvre qu'environ une SCI ; le Pro à 500 €/mois est disproportionné pour CIPL.
- **Iopole** : des frais de mise en place sur devis et un positionnement grands comptes ou éditeurs établis le rendent probablement peu adapté à un micro-éditeur. À confirmer par un devis.

### Gaps
- Super PDP : je ne sais pas si les factures reçues sont facturées en offre API, ni si une SCI rattachée via un éditeur peut rester sur l'offre Compte gratuite. Les paliers chevauchants (10 000 apparaît dans deux paliers) et le mode tranche ou global ne sont pas précisés.
- Prix éditeur de B2Brouter (eDocSync), d'Iopole, de Seqino et de Docoon : non publics.
- Invopop : prix en euros d'un envoi via la PA française (hors Chorus Pro) non indiqué ; usage du plan Dev en production non précisé.

## 4. Multi-sociétés : un compte intégrateur pour plusieurs SIREN, onboarding/KYC séparé, qui signe le contrat

### Takeaway
**Super PDP** : chaque SCI crée son propre compte (KYC du représentant légal, mandat à Super PDP, autorisation du logiciel tiers via OAuth). L'éditeur détient un token par société et paie au tarif de gros (marque grise). **B2Brouter** : un compte par SIREN et des groupes de comptes ; la création de comptes par API (`POST /accounts`) est réservée à l'offre éditeur eDocSync. **Invopop** : enregistrement par « party » (SIREN). **Iopole** : marque blanche, l'éditeur est l'unique interlocuteur, mais la mécanique contractuelle n'est pas documentée.

### Cited Findings
- **Super PDP, parcours d'inscription d'une entreprise** (démo en environnement de test) : 1) confirmation de l'e-mail ; 2) données de la société et du représentant légal ; 3) **mandat autorisant Super PDP à gérer les échanges de factures** ; 4) inscription facultative de l'adresse de facturation à l'annuaire ; 5) vérification d'identité par QR code sur mobile ; 6) **autorisation du logiciel partenaire à gérer le compte**. Les éditeurs (facturation, ERP, caisse) peuvent intégrer Super PDP par API et revendre le service ; l'intégrateur Odoo Akretion est cité — [digitiz.fr (16/10/2026)](https://digitiz.fr/superpdp/).
- Super PDP : flux OAuth2 *Authorization Code* où le logiciel redirige vers le « tunnel d'inscription SUPER PDP » et récupère un token à la fin — [erp.go](https://raw.githubusercontent.com/superpdp/examples/main/erp.go). Marque grise : « La marque SUPER PDP apparaît à l'inscription du client », l'éditeur paie au tarif de gros — [superpdp.tech/tarifs](https://www.superpdp.tech/tarifs).
- **B2Brouter** : le compte parent est toujours un SIREN (`cin_scheme "0002"`, créé par `POST /accounts`) ; les établissements sont des unités organisationnelles (`parent_id`) ; l'activation de `POST /accounts/{id}/tax_report_settings` (DGFiP) inscrit la société à l'Annuaire, avec publication le lendemain matin après le batch de nuit — [guide France](https://docs.b2brouter.net/en/developers/guides-by-country/france/dgfip-e-invoicing-and-e-reporting/). **Création de comptes par API seulement avec eDocSync** : en eDocExchange, les comptes s'ajoutent via l'onglet Developers de l'application web et il faut des droits Admin/Owner sur chaque compte — [docs.b2brouter.net, Account](https://docs.b2brouter.net/en/developers/essential-guides/account/). Une page « Verify your identity » existe, sans détail lu.
- **Invopop** : l'enregistrement est « a one-time, per-party prerequisite » ; chaque SIREN doit être inscrit à l'Annuaire et publié sur Peppol ; KYC, mandat et signataire ne sont pas décrits sur cette page — [docs.invopop.com](https://docs.invopop.com/guides/fr-pa.md).
- **Iopole** : marque blanche, Iopole reste invisible et l'éditeur reste l'unique interlocuteur de ses clients — [codeur.com (sponsorisé Iopole)](https://www.codeur.com/blog/plateforme-agreee-editeur-de-logiciels/). Signataire du contrat et multi-SIREN non précisés — [facture-electronique-en-ligne.fr](https://facture-electronique-en-ligne.fr/avis-logiciel/iopole).
- **Seqino** : marque grise (connexion API qui permet aux clients d'utiliser le statut PA de Seqino) ou marque blanche (l'éditeur devient lui-même PA, avec une immatriculation accélérée et des audits annuels) — [seqino.com](https://seqino.com/api-pdp-marque-blanche-grise-facture-electronique/) ; [comparepdp.com](https://comparepdp.com/articles/api-facturation-electronique).

### Inferences
- Chez Super PDP, le contrat d'usage et le mandat sont signés par chaque SCI (CGU et mandat Super PDP), tandis que la relation commerciale et la facture sont portées par l'éditeur (CIPL) en marque grise. C'est le même schéma « 1 compte + 1 token par société » que chez Pennylane, mais à coût marginal quasi nul.
- Chez B2Brouter, pour qu'un éditeur crée les comptes de ses SCI par API, il faut passer par eDocSync (sur devis). Sinon, chaque SCI s'inscrit elle-même et CIPL utilise une clé API par compte ou par groupe.

### Gaps
- Je n'ai trouvé chez aucun candidat de texte contractuel (CGU partenaire) qui précise qui est le « client » légal de la PA. Il faut le demander à Super PDP et à B2Brouter.
- Je ne sais pas si un même utilisateur Super PDP peut gérer plusieurs sociétés depuis un seul identifiant, ni s'il existe une API de création de compte côté partenaire au-delà du tunnel OAuth.

## 5. Réception des factures fournisseurs incluse ?

### Takeaway
La réception est incluse et accessible par API chez Super PDP (polling `GET /v1.beta/invoices?starting_after_id`, webhooks annoncés) et chez B2Brouter (plans payants, webhooks, réception Peppol 0225). Chez Invopop, la réception n'est pas documentée dans les pages lues. Chez Iopole, elle n'est pas détaillée.

### Cited Findings
- Super PDP : l'exemple officiel relève par polling, côté acheteur, la facture envoyée par le vendeur (`GET /v1.beta/invoices?starting_after_id=${maxId}`) — [quick_start.js](https://raw.githubusercontent.com/superpdp/examples/main/quick_start.js). L'offre Compte gratuite couvre l'envoi et la réception — [superpdp.tech/tarifs](https://www.superpdp.tech/tarifs) ; [digitiz.fr](https://digitiz.fr/superpdp/).
- B2Brouter : réception via Peppol 0225, « Receives invoices from any French or Peppol-connected platform » — [guide France](https://docs.b2brouter.net/en/developers/guides-by-country/france/dgfip-e-invoicing-and-e-reporting/). « Réception de factures électroniques » est incluse en Professional et Business ; c'est incohérent pour Basic — [b2brouter.net/fr/tarifs](https://www.b2brouter.net/fr/tarifs/). Un guide développeur « Receive, integrate and manage received invoices » existe — [docs.b2brouter.net](https://docs.b2brouter.net/en/get-started/overview/).
- Invopop : les pages lues ne mentionnent ni webhooks ni réception B2B ; seule la réception de factures du secteur public (Chorus Pro) est citée — [docs.invopop.com](https://docs.invopop.com/guides/fr-pa.md). La page pricing cite des actions « Import invoice from SDI » (Italie), mais rien de propre à la France — [invopop.com/pricing](https://www.invopop.com/pricing).
- Iopole : statut « reçu » mentionné, réception non détaillée — [facture-electronique-en-ligne.fr](https://facture-electronique-en-ligne.fr/avis-logiciel/iopole).

### Inferences
- Pour les SCI de CIPL, qui doivent pouvoir recevoir depuis le 1er septembre 2026, Super PDP et B2Brouter couvrent émission et réception dans la même intégration.

### Gaps
- Coût de la réception en offre API chez Super PDP (compte-t-elle comme une « facture » ?) ; format de livraison des factures reçues (Factur-X d'origine ou JSON EN 16931) chez Super PDP et B2Brouter.

## 6. Synthèse comparative : quelle PA intégrer pour CIPL ?

### Takeaway
Pour un micro-éditeur qui produit déjà des Factur-X pour quelques SCI, **Super PDP** est l'option la plus économique et la plus simple : OAuth par société, dépôt de fichier, coût de l'ordre de quelques euros par an et par SCI. Ses risques : une API en bêta, une production depuis mai 2026, une date d'immatriculation à confirmer. **B2Brouter** est l'option la plus mûre et la mieux documentée (import Factur-X explicite, mapping CDV, staging, versions datées), mais plus chère par SCI (110 € HT par an en Professional) et sur devis côté éditeur. Iopole et Invopop paraissent surdimensionnés ou mal alignés. Seqino et Docoon restent à sonder par devis.

### Inferences
- Shortlist à demander : **1) Super PDP**.
