# Domaine D3 — Abonnement et comptes

Revue 16c, lecture seule, du 31/10/2026. Fichiers lus : `AbonnementCloud`, `RegleAbonnement`, `SectionAbonnement`, `RegleInscription`, `EcransCloud`, `SectionUtilisateurs`, `UtilisateursCloud`, `SessionCloud`, `CloudClient`, `DemarrageCloud`, `PremiersPas`, `VisiteGuidee`, `BatimentExemple`, `MiseAJour`, `Trousseau`, `Dpapi`, et côté serveur `abonnement-stripe.ts`, `stripe-webhook.ts`, `emails-abonnement.ts`, les SQL des étapes 2, 4, 9a, 9b, 9c1, 9c2, 10, 10b, 13, 14, 16, plus `CIPL.iss`.

Le serveur tient bien la lecture seule (déclencheur sur toutes les tables, même règle qu'en C#) et les licences ; les trous sont ailleurs : une installation neuve n'a pas l'adresse du cloud, les droits « admin seulement » sur le RIB ne sont pas vérifiés par le serveur, le changement d'entreprise perd une saisie en cours sans prévenir, et deux détails Stripe peuvent coûter de l'argent.

### D3-01 · Majeur (bloquant pour la vente) · Une installation neuve n'a ni adresse ni clé du cloud : CIPL ne démarre pas chez un client
- Où : `Assets/Script/Facturation/ReglageService.cs:85-86` et `:250-253` ; `Assets/Script/Cloud/DemarrageCloud.cs:21-25` ; `Installeur/CIPL.iss:53-54` ; `Assets/Editor/EssaiCloudWindow.cs:69`.
- Problème : l'adresse et la clé publique du projet Supabase sont lues dans `persistentDataPath/cipl_app_secrets.dat`, que seule la fenêtre de l'éditeur (CIPL › Essai cloud) écrit. L'installeur ne copie que le build (`Source: "{#Source}\*"`), rien dans `AppData`, et aucune valeur par défaut n'est compilée. Les parcours AS ont tous tourné sur le PC de développement, où le fichier existe déjà.
- Scénario : un client installe `CIPL-installation.exe` sur son PC → lancement → `SessionCloud.Configure` faux → message « Adresse du projet cloud non renseignée : dans Unity, menu CIPL › Essai cloud (étape 1). » et plus rien. Ni « Créer mon compte », ni « J'ai reçu une invitation ».
- Correction proposée : deux constantes compilées (`UrlDefaut`, `CleDefaut` ; la clé est publique, elle peut être dans le code) utilisées quand le fichier est vide ; le fichier reste une surcharge pour viser un projet de test. Le message d'erreur ne doit plus parler d'Unity à un client.
- Test : EditMode : `ReglageService.GetCloudUrl()` et `GetCloudCle()` non vides quand `cipl_app_secrets.dat` est absent (le test renomme le fichier puis le remet). Play : installer sur un autre compte Windows (où `LocalLow\CIPL\CIPL` est vide) → l'écran de connexion s'affiche.
- Confiance : haute (flux suivi de `Lancer` au fichier ; aucun autre écrivain dans le dépôt, `ConstruireInstalleur.cs` ne mentionne ni secrets ni `LocalLow`).

### D3-02 · Majeur · Les droits « admin seulement » sur le RIB, le logo et les listes de charges ne sont pas vérifiés par le serveur
- Où : `Serveur/etape9a_supabase.sql:40-58` (`enregistrer_reglages`) ; `Assets/Script/Facturation/ReglagePanel.cs:38`, `:715`, `:771`, `:1299` (`_reserveAdmin`) ; champs `Assets/Script/Facturation/ReglageData.cs:74`, `:79`, `:87`.
- Problème : la décision du 11/10 (RIB, logo, suppression d'une liste de charges réservés à l'admin) n'existe que dans l'interface : `_reserveAdmin` cache les champs. `enregistrer_reglages` accepte n'importe quel `p_data` de n'importe quel membre (`mes_acces` + contrôle de version ; l'admin n'est exigé qu'à la version 0). Un « utilisateur » qui appelle la fonction REST avec son propre jeton (clé publique et adresse lisibles dans `cipl_app_secrets.dat`) change l'IBAN imprimé sur toutes les factures.
- Scénario : Odile (rôle utilisateur) envoie `POST /rest/v1/rpc/enregistrer_reglages` avec les Réglages courants où `ribs[0].iban` est le sien → `{ok: true}` → les factures suivantes de SCI Rivoli portent son IBAN. L'admin ne s'en aperçoit qu'en relisant le RIB.

- Test : EditMode sur le texte du SQL (comme `Les_fonctions_des_emails_sont_reservees_au_serveur`) : `enregistrer_reglages` contient le contrôle sur `ribs`, `logoPath`, `listesCharges`. Parcours : connectée en utilisateur, un appel REST avec un RIB changé → refus `admin`.
- Confiance : haute. Classé Majeur et non Critique : il faut un membre invité et un appel REST à la main ; les membres sont des collègues de confiance. Mais c'est bien une règle annoncée que le serveur ne tient pas.

### D3-06 · Majeur · `inscrire` accepte n'importe quel compte connecté : l'adresse e-mail n'est prouvée que côté client
- Où : `Serveur/etape13_supabase.sql:12-25` ; `Assets/Script/Cloud/CloudClient.cs:52-54` ; `Assets/Script/Cloud/SessionCloud.cs:131-146` et `:273-308`.
- Problème : « Confirm email » est décoché (décision 9b), donc `POST /auth/v1/signup` avec n'importe quelle adresse rend une session tout de suite, sans boîte mail. `inscrire` n'exige que `auth.uid()` : le code à 6 chiffres de l'étape 13 n'est imposé que par la fenêtre de CIPL. Un script peut créer des comptes aux adresses d'autrui et des groupes d'essai ; les e-mails de l'étape 14 (J-7, J-1, fin) partent alors du Gmail de CIPL vers des adresses choisies par l'attaquant. Second effet : une adresse « squattée » avec un mot de passe fait échouer « J'ai reçu une invitation » chez son vrai propriétaire (`Rejoindre` → 422 → `SeConnecter` avec le mot de passe tapé → « E-mail ou mot de passe incorrect »), jusqu'à ce qu'il pense à « Mot de passe oublié ».
- Scénario : `curl /auth/v1/signup {email: dupont@sci-x.fr, password: x}` → session → `rpc/inscrire {particulier, « Patrimoine de X »}` → `{ok: true}` ; M. Dupont reçoit « Votre essai CIPL se termine dans 7 jours » sans avoir jamais entendu parler de CIPL.
- Correction proposée : dans `inscrire`, exiger que la session vienne du code e-mail : `if not (coalesce(auth.jwt() -> 'amr', '[]'::jsonb) @> '[{"method":"otp"}]') then raise exception 'adresse non prouvée'; end if;` (`/auth/v1/verify` type `email` donne `amr` = `otp`, une connexion par mot de passe donne `password`). Rien à changer côté client.
- Test : parcours : `signup` par curl puis `rpc/inscrire` → refus ; le parcours AO (code reçu) passe toujours. EditMode : le texte du SQL contient `amr`.
- Confiance : haute sur le trou (SQL et flux lus) ; moyenne sur la correction exacte (vérifier la forme de la revendication `amr` sur un jeton réel).

### D3-07 · Majeur · Stripe « unpaid » (relances épuisées) laisse le groupe modifiable sans payer
- Où : `Serveur/fonctions/stripe-webhook.ts:26-30` ; `Serveur/etape9c1_supabase.sql:12-16`.
- Problème : `statut("unpaid")` → `refuse` → `ecriture_permise` vraie. Chez Stripe, `unpaid` est l'état après l'échec de toutes les relances quand le réglage « paiements échoués » est « marquer comme impayé » : l'abonnement reste, les factures restent ouvertes, plus aucune tentative. CIPL reste alors modifiable sans limite. La décision §13 (« Stripe relance 3 fois, puis expiration ») n'est vraie que si le réglage Stripe est « annuler l'abonnement » ; avec « laisser en retard », `past_due` dure aussi sans fin.
- Scénario : carte refusée, 3 relances échouées, réglage Stripe sur « impayé » → `customer.subscription.updated` status `unpaid` → `groupes.statut = 'refuse'` pour toujours → saisie et factures continuent, rien n'est payé.
- Correction proposée : `unpaid` sur la ligne `expire` (un mot). Noter dans la liste de l'étape 17 : réglage Stripe « annuler l'abonnement » après les relances, pour que `past_due` ne dure pas.
- Test : EditMode sur le texte du `.ts` : `"unpaid"` est sur la ligne qui rend `"expire"`. Stripe test (horloge de test) : abonnement passé `unpaid` → bandeau corail.
- Confiance : moyenne : dépend du réglage du tableau de bord Stripe, qui n'est pas dans le dépôt.

### D3-13 · Mineur · Hygiène de la session : jeton jamais invalidé côté serveur, copie locale rendue sans vérifier le propriétaire du jeton

- **Lecture seule à l'expiration** : `ecriture_permise` et le déclencheur `abonnement_expire` sur `batiments`, `locataires`, `documents`, `reglages`, `secrets` et la prise de `verrous` ; `RegleAbonnement.Lire` applique la même règle avec la date du serveur (`aujourdhui`) ; `ajouter_entreprise`, `changer_siret` et `pappers.ts` vérifient `ecriture_permise` ; côté client, `EcritureCloud.Enregistrer`, `ReglageService.Save` / `EcrireEtPartager`, `FactureEnvoiAuto`, `FactureElectronique` et la tournée de l'annuaire s'arrêtent sur `AbonnementCloud.LectureSeule` ; `Constater` fait apparaître le bandeau au premier refus (quand l'abonnement a été lu, voir D3-12). L'export reste possible pour tous à l'expiration (`RegleExport.PeutExporter`).
- **Prix et dates** : mêmes prix des deux côtés (40 / 28 / 15 € HT, annuel = 10 mois, TVA 20 %) ; même règle des 48 h pour le premier prélèvement (`PremierPrelevement` et `trial_end`) ; essai modifiable jusqu'au dernier jour inclus des deux côtés (`fin_essai >= current_date`).
- **Webhook Stripe** : signature vérifiée, état relu chez Stripe plutôt que pris dans l'événement, `stripe_abonnement` remis à nul à l'expiration (un nouveau `choisir` redevient possible, sans nouvel essai), répartition appliquée à la création seulement, résiliation / reprise cohérentes, e-mails d'étape 14 décidés sur l'état relu ; page de retour sans donnée.
- **Licences** : `inviter`, `changer_acces`, `ajuster` et `choisir` refusent de descendre sous le nombre utilisé (accès + invitations en cours) ; les invitations expirées ne comptent plus ; une nouvelle invitation remplace la précédente pour la même adresse ; dernier admin et « soi-même » refusés dans `changer_role`, `retirer_membre`, `changer_acces` ; 3 licences par entreprise en essai, 1 pour une entreprise ajoutée à un groupe abonné.
- **Rôles** : toutes les fonctions d'administration passent par `groupe_admin` → `est_admin` (rôle admin **et** accès à l'entreprise) ; `definir_secret`, `definir_mode_documents`, `forcer_verrou` admin côté serveur ; `abonnement-stripe.ts` exige `groupe_admin` ; `messagerie.ts` et `facture-electronique.ts` vérifient `mes_acces` / `est_admin` ; les fonctions de l'étape 14 sont réservées à `service_role` et `emails-abonnement` refuse sans la clé du coffre ou la clé service. Dans l'interface : onglets selon le rôle (`Onglets`, testé), sections Utilisateurs / Abonnement / Export visibles selon `EstAdmin`, bandeaux avec bouton pour l'admin seul.
- **Invitations** : code de 8 caractères sur 32 (environ 40 bits), seule l'empreinte SHA-256 en base, comparaison avec l'adresse du compte **connecté** (un attaquant doit posséder la boîte mail et le code), expiration 7 jours vérifiée, renvoi avec nouveau code, annulation libère la licence, `Exclu` ferme l'entreprise chez la personne retirée dans les 30 s.
- **Mot de passe oublié** : code Supabase (`recover` / `verify`), session de récupération gardée pour réessayer un mot de passe refusé sans nouveau code, « Rester connecté » conservé selon le choix d'avant ; depuis le menu Compte, l'adresse n'est pas modifiable.
- **Inscription (côté client)** : formulaire contrôlé (`RegleInscription.Refus`, testé), société fermée ou introuvable refusée avant le code, `deja_membre` et `siret` vérifiés avant le code et de nouveau dans `inscrire`, mot de passe posé après `inscrire` (une adresse refusée garde le sien), Réglages de départ sans le logo ni le serveur d'envoi de CIPL. `adresse_deja_membre` et `siret_deja_sur_cipl` ouverts sans connexion : décision acceptée le 25/10.
- **Connexion gardée** : seul le jeton de renouvellement est écrit, chiffré DPAPI (même compte Windows, même PC), fichier séparé pour l'éditeur ; jeton refusé (4xx) effacé, panne réseau conservé ; Mac : trousseau par `security` (limite assumée par un `ponytail:`). La clé du cloud est publique ; aucun jeton n'est journalisé.
- **Changement d'entreprise et déconnexion** : `DirectCloud.Arreter`, `FermerEcrans` (libère les verrous), `_bm.Vider()` avant `Installer`, Réglages et secrets relus depuis le serveur dans un fichier **par entreprise** (`cipl_reglages_<id>.json`, `cipl_secrets_<id>.dat`), racine des documents par entreprise, copie locale par entreprise ; `Oublier` + `CopieLocale.Effacer` + `Vider` à la déconnexion. Hors de la fenêtre décrite en D3-10, aucune donnée d'une entreprise ne passe dans une autre.
- **Premiers pas, visite, exemple** : « Visite vue » retenu même sur « Passer » (`Finir` appelle `fin` dans les deux cas), choix gardés dans le compte (tous les PC), bâtiment d'exemple exclu des comptes et des guides.
- **Mise à jour** : jamais dans l'éditeur, fenêtre obligatoire devant tout, installeur lancé à la vraie fermeture (après la garde), bilan au lancement suivant ; dépôt et liens en HTTPS.

Hors domaine, à signaler aux revues voisines : le mot de passe SMTP et la clé Pennylane sont partagés à tous les membres (règle `secrets_lecture`) et écrits en clair dans `cipl_secrets_<id>.dat` du PC de chacun (décision du 15/10, domaine Réglages) ; n'importe qui connaissant un SIRET public peut l'« occuper » par une inscription et bloquer la vraie société (« demandez une invitation à son administrateur »), limite du choix « SIRET unique sur CIPL », à prévoir au support.
