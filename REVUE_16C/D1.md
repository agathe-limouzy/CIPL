# Domaine D1 — Serveur et sécurité

**État général** : la base est saine. RLS en lecture seule sur toutes les tables, écritures seulement par des fonctions `security definer` avec `search_path = public` qui vérifient `mes_acces()` / `est_admin()` / `groupe_admin()`, clé composite `(entreprise_id, …)` partout, webhook Stripe signé et relu chez Stripe, verrous et versions décidés en une seule instruction SQL. Aucun chemin trouvé pour lire ou écrire les données d'une autre entreprise.
**Défauts** : 2 Critiques, 7 Majeurs, 7 Mineurs.
**Les plus graves** : le chemin d'un document n'est pas contrôlé par le serveur et les PC des collègues l'écrivent tel quel ; une clé d'API de CIPL peut revenir au client dans un message d'erreur ; le serveur n'applique pas « RIB et logo réservés à l'admin ».

### D1-01 · Critique · `documenter` n'encadre pas le chemin ; les PC des collègues l'écrivent tel quel
- Où : `Serveur/etape6_supabase.sql:39-48` (`documenter`, aucun contrôle de `p_chemin`) ; `Assets/Script/Cloud/DocumentsCloud.cs:344` (`Absolu` = `Path.Combine(racine, chemin)`), `:228-231` (lignes du serveur reprises sans passer par `SyncDocuments.Partage`), `:420-428` (`Telecharger` crée le dossier et écrit à `abs`) ; `DocumentsCloud.cs:85-105` (`SyncDocuments.Redresser` garde tout chemin qui ne commence pas par `Batiment/`).
- Problème : le serveur enregistre le `chemin` reçu sans le vérifier. Chaque PC de l'entreprise (mode « Dans CIPL ») le combine à sa racine avec `Path.Combine`, qui ignore la racine quand le second argument est un chemin complet, et qui laisse les segments `..` remonter. Le filtre `Partage` (sous `Batiment/`, `Logo/`…) ne s'applique qu'aux fichiers du PC, pas aux lignes venues du serveur.
- Scénario : une ligne `documents` dont `chemin` est un chemin complet ou contient `..` (saisie par un compte membre, ou par un client modifié) → dans les 20 s, le passage de synchronisation de chaque collègue télécharge le contenu et l'écrit en dehors du dossier de l'entreprise.
- Correction proposée : dans `documenter` et `supprimer_document`, refuser (`raise exception`) un `p_chemin` qui ne commence pas par l'une des racines partagées, qui contient un segment `..`, un `\` ou un `:`. Côté client, en défense en profondeur : ignorer les lignes du serveur pour lesquelles `SyncDocuments.Partage(c)` est faux, et dans `Telecharger` vérifier que `Path.GetFullPath(abs)` commence par `Path.GetFullPath(racine) + séparateur`.
- Test : EditMode — `SyncDocuments.Plan` ne doit produire aucune action `Telecharger` pour un chemin hors racines (après filtrage) ; test texte sur `etape6_supabase.sql` vérifiant la présence du contrôle de `p_chemin` dans `documenter`. Serveur : appeler `documenter` avec `p_chemin = '../x'` → exception.
- Confiance : haute (comportement de `Path.Combine` et de `Redresser` lus ; aucun filtre sur le trajet serveur → disque).

### D1-02 · Critique · La clé Pappers et la clé Google Maps sont dans l'adresse appelée ; un échec réseau la renvoie au client
- Où : `Serveur/fonctions/pappers.ts:76` (`api_token=` dans l'URL) et `:93-95` (`catch` → `erreur: e.message`, statut 500) ; `Serveur/fonctions/cartes.ts:39-46` (`key: CLE` dans l'URL) et `:49-51` (même `catch`).
- Problème : quand `fetch` échoue (DNS, connexion refusée, coupure), Deno lève une `TypeError` dont le message contient l'URL complète. Le `catch` renvoie ce message à CIPL dans `erreur`. La clé secrète de CIPL quitte donc le serveur, vers le PC du client (journal Unity, message « Détail technique »).
- Scénario : Pappers injoignable pendant la tournée → `FicheServeur` reçoit `{refus:"erreur", erreur:"error sending request for url (https://api.pappers.fr/…api_token=…)"}` → le client en a la clé.
- Correction proposée : Pappers accepte la clé dans l'en-tête `api-key` : l'y mettre. Pour Google Maps (clé obligatoirement dans l'URL) et par sûreté partout : entourer le `fetch` d'un `try/catch` qui renvoie un message fixe (`refus: "pappers"` / `"google"`, `erreur: "injoignable"`), et ne jamais renvoyer `e.message` d'un `fetch` au client.
- Test : test texte EditMode sur `pappers.ts` (pas de `api_token=` dans une URL ; présence de `"api-key"`) et sur `cartes.ts` (le `catch` externe ne renvoie pas `e.message`). Serveur : lancer la fonction localement sans réseau et vérifier que la réponse ne contient pas la clé.
- Confiance : moyenne — le format du message d'erreur de `fetch` sous Deno (qui cite l'URL) est à confirmer sur la version déployée ; le trajet `catch → erreur → client` est certain.

### D1-03 · Majeur · Le serveur laisse un « Utilisateur » modifier les RIB, le logo et les listes réservés à l'admin
- Où : `Serveur/etape9a_supabase.sql:40-58` (`enregistrer_reglages` : seul `mes_acces()` est exigé quand `p_version > 0`) ; règle côté client seulement : `Assets/Script/Facturation/ReglagePanel.cs:715, 771, 1001` (`_reserveAdmin`) ; données concernées : `Assets/Script/Facturation/ReglageData.cs:74` (`ribs`, dont `iban` ligne 21), `logoPath`.
- Problème : la décision (CONCEPTION §16, « Admin seulement : RIB, logo, suppression d'une liste de charges ») n'est appliquée que par l'écran. `enregistrer_reglages` accepte tout le `ReglageData` de n'importe quel membre. Le projet pose pourtant le serveur comme juge (« le serveur refuse déjà ce qui n'est plus permis », REVUE 9b). Le RIB imprimé sur les factures est une donnée d'argent.
- Scénario : un membre « utilisateur » envoie `enregistrer_reglages` avec un `ribs[0].iban` changé (appel direct à l'API, avec son propre jeton) → accepté ; les prochaines factures de tous portent cet IBAN.
- Correction proposée : dans `enregistrer_reglages`, si `not est_admin(p_entreprise)`, comparer `p_data->'ribs'`, `p_data->'logoPath'`, `p_data->'sansLogo'` et le nombre d'éléments des listes de charges à la ligne en place ; en cas de différence, répondre `{ok:false, refus:'admin'}` (déjà prévu dans le contrat de la fonction).
- Test : test texte EditMode sur `etape9a_supabase.sql` (présence de `est_admin` dans la branche `p_version > 0` et de `'ribs'`) ; serveur : un compte « utilisateur » appelle `enregistrer_reglages` avec un IBAN changé → `refus: admin` ; avec un texte d'entête changé → `ok`.
- Confiance : haute.

### D1-04 · Majeur · `creer_entreprise_import` reste ouverte à tout compte et contourne les règles d'`inscrire` et d'`ajouter_entreprise`
- Où : `Serveur/etape2_supabase.sql:137-159` (création d'un groupe en essai + entreprise, 3 licences, aucune des règles postérieures) ; appelant unique : `Assets/Script/Cloud/DonneesCloud.cs:91-98`, proposé par `DemarrageCloud.cs:100-104` seulement quand l'utilisateur n'a aucune entreprise ou reprend un import.
- Problème : la fonction date de l'étape 2 et n'a pas suivi : pas de refus « déjà membre d'un groupe » (`inscrire`, etape13:21-25), pas d'`ecriture_permise` ni de licence à 1 pour un groupe abonné (`ajouter_entreprise`, etape10b:150-163), pas de SIRET. Elle est accordée à `authenticated`. L'écran ne l'offre presque jamais, mais l'API l'offre toujours.
- Scénario : un compte dont le groupe est expiré (lecture seule) appelle `creer_entreprise_import('X')` → nouveau groupe en essai 14 jours à son nom, modifiable, 3 licences ; répétable. Autre cas : un admin d'un groupe abonné l'appelle → entreprise ajoutée avec 3 licences sans passage par Stripe.
- Correction proposée : dans `creer_entreprise_import`, (1) si l'utilisateur est titulaire ou admin d'un groupe, exiger `ecriture_permise(g)` et donner `licences_max = case when statut = 'essai' then 3 else 1 end` comme `ajouter_entreprise` ; (2) s'il est membre d'un groupe sans en être admin, refuser ; (3) sinon créer le groupe comme aujourd'hui. Plus simple encore : faire appeler `ajouter_entreprise` par l'import quand une entreprise existe déjà, et réserver `creer_entreprise_import` au cas « aucun groupe ».
- Test : test texte EditMode (présence d'`ecriture_permise` et de `licences_max` dans la fonction) ; serveur : compte déjà membre non admin → refus ; groupe expiré → refus.
- Confiance : haute.

### D1-05 · Majeur · `choisir` peut créer un second abonnement Stripe pour le même groupe
- Où : `Serveur/fonctions/abonnement-stripe.ts:80-81` (seul `groupe.stripe_abonnement` est regardé) ; `stripe-webhook.ts:42-49` (`appliquer` écrase `stripe_abonnement` avec le dernier événement reçu).
- Problème : `stripe_abonnement` n'est rempli qu'à l'arrivée du webhook. Tant qu'il est nul (webhook en retard, échoué, ou page de paiement ouverte deux fois), `choisir` ouvre une nouvelle session Checkout. Deux paiements → deux abonnements facturés ; CIPL n'en connaît qu'un, l'autre continue d'être prélevé sans être visible.
- Scénario : l'admin paie ; le webhook répond 500 (relancé plus tard par Stripe) ; CIPL affiche encore « Choisir l'abonnement » ; l'admin repaie → deux `sub_…` actifs pour le même `cus_…`.
- Correction proposée : dans `choisir`, quand `groupe.stripe_client` existe, lire `stripe.subscriptions.list({ customer, status: "all" })` ; s'il en reste une non `canceled`/`incomplete_expired`, l'appliquer au groupe (même code que `appliquer`) et répondre « Un abonnement est déjà en cours ».
- Test : test texte EditMode (présence de `subscriptions.list` dans la branche `choisir`) ; en bac à sable Stripe : payer, couper le webhook, relancer « Choisir » → refus.
- Confiance : moyenne (dépend du retard réel du webhook ; le code ne s'en protège pas).

### D1-06 · Majeur · `etat` échoue quand Super PDP ne répond pas : la SCI est vue « non reliée » et ses loyers ne sont jamais préparés pour la plateforme
- Où : `Serveur/fonctions/facture-electronique.ts:86-97` (`etat` appelle `jeton()` puis `oauth2_sessions/me` à chaque fois ; un `fetch` qui lève remonte au `catch` ligne 205 → 500) ; `Assets/Script/Facturation/FactureElectronique.cs:39-49` (`Etat()` ne pose `_active` que si `r.ok`), `:81-83` (`Concerne` exige `Active`), `:159-169` (`Demarrer` : un seul `Etat()` au lancement).
- Problème : la fonction dépend d'un appel en direct à Super PDP pour dire si la SCI est reliée, alors que `plateformes.statut` est déjà gardé en base. Pendant une panne (constatée le 30/10), `Etat()` échoue, `Active` reste faux, et chaque loyer émis dans la session part par e-mail seul, sans `plateformeDonnees` : il ne sera jamais transmis à la plateforme (le rattrapage ne concerne que les factures déjà préparées).
- Scénario : Super PDP en panne à 9 h ; l'admin ouvre CIPL et émet trois loyers de locataires assujettis → trois factures hors plateforme, à corriger plus tard par facture rectificative.
- Correction proposée : dans `etat`, entourer `jeton()` + `oauth2_sessions/me` d'un `try` ; si l'échec n'est pas `invalid_grant`, répondre `{ok:true, relie:true, statut: lien.statut, indisponible:true}` (dernier état connu). Côté CIPL, `Etat()` pose alors `_active` d'après ce statut.
- Test : EditMode — un `Reponse { ok=true, relie=true, statut="verified" }` rend `Active` vrai ; test texte sur le `.ts` (branche `etat` sans dépendance au succès du `fetch`). Serveur : couper la sortie réseau de la fonction → réponse 200 avec le statut gardé.
- Confiance : haute.

### D1-07 · Majeur · Renouvellement du jeton Super PDP non protégé contre deux appels simultanés
- Où : `Serveur/fonctions/facture-electronique.ts:53-68` (`jeton()` : lecture de la ligne, refresh, puis écriture ; ponytail ligne 62) ; `:61` (`invalid_grant` → `refus: "retire"`) ; consommateurs : `etat` (chaque ouverture de CIPL par chaque membre, `Demarrer`) et `envoyer`.
- Problème : Super PDP change le jeton de renouvellement à chaque usage. Deux sessions qui lisent la même ligne et renouvellent en même temps : la seconde présente un jeton déjà consommé → `retire`. Le ponytail prévoit le refus, pas sa conséquence : pour ce membre, `Etat()` échoue (même effet que D1-06 : loyers émis hors plateforme), et si Super PDP applique la règle OAuth 2.1 « réutilisation = révocation de la famille », le lien de la SCI est rompu pour tous jusqu'à ce que le gérant refasse « Activer ».
- Scénario : deux collègues ouvrent CIPL à la même seconde après la nuit (jeton d'accès expiré) → deux `etat` → deux refresh avec le même `refresh_token`.
- Correction proposée : après un `invalid_grant`, relire la ligne `plateformes` ; si `refresh_token` a changé depuis la lecture et `expire_le` est à venir, utiliser son `access_token` et ne pas répondre `retire`. Ou sérialiser : `update … set … where refresh_token = <ancien>` et, si 0 ligne, relire. La marge de 60 s (ligne 54) peut passer à 5 min pour réduire la fenêtre.
- Test : test texte EditMode (la branche `invalid_grant` relit la ligne avant de répondre `retire`) ; serveur, en bac à sable : lancer deux `etat` en parallèle sur une SCI dont le jeton est expiré → deux `ok`.
- Confiance : moyenne (la fenêtre est courte ; la règle de révocation de Super PDP n'est pas documentée ici).

### D1-08 · Majeur · `ajuster` écrit les licences en base avant Stripe et ne valide pas `licences`
- Où : `Serveur/fonctions/abonnement-stripe.ts:150-158` (mise à jour `entreprises.licences_max` et `groupes` avant), `:162` (quantité Stripe ensuite), `:150` (`licences` non vérifié : entier, positif).
- Problème : si l'appel Stripe échoue (réseau, carte, 500), la base a déjà le nouveau nombre de licences mais la facture Stripe non. Le webhook ne recopie `licence.quantity` que dans `groupes.licences_max`, jamais dans `entreprises`. L'écart reste jusqu'au prochain `ajuster` réussi. Une valeur non entière (`1.5`) est acceptée en base puis refusée par Stripe (500 pour le client).
- Scénario : l'admin passe de 3 à 6 licences ; Stripe renvoie une erreur → CIPL affiche l'erreur, mais `inviter` accepte déjà 6 personnes, et Stripe en facture 3.
- Correction proposée : valider `Number.isInteger(licences) && licences >= 1` ; appeler `subscriptionItems.update` d'abord, puis écrire en base ; ou, dans le `catch`, remettre l'ancienne valeur.
- Test : test texte EditMode (ordre des appels : `subscriptionItems.update` avant `.from("entreprises").update` ; présence de `Number.isInteger`) ; serveur en bac à sable : `licences: 1.5` → refus propre.
- Confiance : haute (ordre lu) ; fréquence faible.

### D1-09 · Majeur · Clé Pennylane et mot de passe SMTP en clair sur le disque, alors que le jeton de session est chiffré

### D1-10 · Mineur · Les révocations oublient `authenticated` : plusieurs fonctions « internes » restent appelables par tout compte
- Où : `Serveur/etape9c1_supabase.sql:97-102` (`ecriture_permise`, `refuser_si_expire` : `revoke … from public, anon` seulement) ; `etape10b_supabase.sql:168-171` (`licences_utilisees_entreprise`, `entreprises_licences`) ; `etape9b_supabase.sql:188-197` (`groupe_admin`, `licences_utilisees` explicitement accordées à `authenticated`) ; `etape2_supabase.sql:69-81` (`mes_acces`, `est_admin` : aucune clause).
- Problème : Supabase pose des privilèges par défaut qui accordent `execute` à `anon`, `authenticated` et `service_role` sur toute nouvelle fonction de `public`. `revoke … from public, anon` ne retire donc pas `authenticated`. L'étape 14 l'a fait correctement (`from public, anon, authenticated`) et le test `Les_fonctions_des_emails_sont_reservees_au_serveur` le vérifie ; les étapes précédentes non.
- Scénario : un compte quelconque appelle `entreprises_licences(<uuid d'un groupe>)` → noms et licences des entreprises du groupe (il faut connaître l'uuid ; un membre du groupe les a déjà par `abonnement()`). `ecriture_permise(uuid)` dit si un groupe est expiré.
- Correction proposée : un script `etape16c` qui fait `revoke all … from public, anon, authenticated` sur ces fonctions (les fonctions SQL qui les appellent sont `security definer`, elles n'ont pas besoin du droit de l'appelant) ; garder le `grant` à `authenticated` seulement pour celles que CIPL appelle (`groupe_admin` via `abonnement-stripe.ts`).
- Test : étendre le test texte de l'étape 14 à toutes les fonctions non appelées par CIPL (liste dans le test) : `from public, anon, authenticated`.
- Confiance : moyenne (dépend des privilèges par défaut du projet Supabase ; à vérifier avec `select grantee from information_schema.routine_privileges where routine_name = 'entreprises_licences'`).

### D1-12 · Mineur · Une fonction serveur lente (> 15 s) passe CIPL « hors ligne » pendant 30 s

- Où : `Serveur/fonctions/pappers.ts:60-66` (accès + abonnement), `:71-76` (cache par SIREN, puis appel payant).

- Correction proposée : compter dans `pappers_fiches` (colonne `demande_par` ou table `pappers_journal(entreprise_id, jour, n)`) et refuser `refus: "quota"` au-delà de N nouveaux SIREN par jour et par entreprise (N = quelques dizaines, au-dessus d'une tournée normale).
- Test : serveur — N+1 SIREN différents en un jour → `quota`.
- Confiance : haute (abus volontaire d'un client, non constaté).
